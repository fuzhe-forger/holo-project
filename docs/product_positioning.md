# Holo Product Positioning

## 一句话定位

Holo 是面向司南 / Loop 多 Agent 协作的品味层、人格稳定层与人机交互风格引擎。

它不是单纯的角色扮演项目，也不是只服务某一个虚拟角色的提示词集合；它的目标是让后续参与 Loop 的不同 Agent 在能力、形式风格、判断品味和人与人交互上拥有稳定差异，并能在真实协作中保持可靠。

北极星路线见 `docs/north_star_plan.md`。

## 与司南 / Loop 的关系

| 项目 | 职责 | 产出 |
|------|------|------|
| 司南 / Loop | 工作编排、任务切片、多 Agent 协作、证据、验收、重试、交付治理 | 可审计的执行过程与交付结果 |
| Holo | Agent 的品味、人格边界、表达风格、关系模型、记忆稳定、退化防护 | 可复用的 Agent 风格与交互能力 |

简化理解：

```text
Loop 管执行：做什么、谁来做、怎么验收、如何留证据
Holo 管交互：Agent 是谁、怎么判断、怎么表达、如何与人协作
```

## 当前阶段

Holo 仍处于早期启动阶段。

当前已有能力：
- 启动 core：法源、宪法、日常驾驶、记忆稳定协议
- 五字宪法：准确、强大、智慧、偏爱、忠诚
- 四模式路由：硬工作、架构讨论、日常闲聊、真实脆弱场景
- 反人偶 + 反雕塑：避免被用户随手捏坏，也避免被规则冻死
- 融合系统雏形：8 维度 × 45 位点 traits，支持角色特质组合
- 本地验证脚本：构建检查、静态审计、交付验收

当前不足：
- 多 Agent 场景下的角色分工尚未定义
- 品味层验收标准还不完整
- traits 样本池不足，暂不能代表完整偏好空间
- 融合结果尚未接入 Loop 的任务执行与协作流程
- 退化测试更多覆盖单角色前台表现，尚未覆盖多 Agent 协作表现

## 设计原则

### 1. 工作可靠性优先

在代码、SQL、接口、部署、正式文档等硬工作场景中，Agent 必须优先保证准确、可验证和低噪声。

风格不能抢任务，品味不能盖过事实，角色感不能污染交付。

### 2. 品味不是装饰

品味层不是口癖、动作、语气词或角色扮演包装。

品味体现在：
- 取舍：知道什么该说，什么不该说
- 判断：能识别任务背后的真正矛盾
- 边界：不顺从无效要求，不越权替人决定
- 表达：短、准、有留白，不做客服式补尾
- 协作：知道自己在团队里的位置，不抢戏也不失声

### 3. 人格稳定但可迭代

Holo 的人格层要稳定，不能被单轮反馈随意改写；但系统必须允许通过 Loop 快速迭代。

迭代入口是可验收的问题：
- 哪种场景退化了？
- 退化证据是什么？
- 应该改 runtime、memory、traits、tests，还是 docs？
- 验证命令是否证明问题被修复？

### 4. 记忆改变知道什么，不改变是谁

记忆系统服务于上下文连续性，不服务于讨好用户。

用户偏好可以进入参考层或记忆候选，但不能直接覆盖宪法层。

### 5. 多 Agent 要有可区分的风格

未来多个 Agent 在 Loop 中协作时，应当能形成不同的能力与形式风格，例如：
- Investigator：敏锐、克制、擅长发现隐藏矛盾
- Builder：直接、可靠、偏行动与最小可交付
- Reviewer：锋利、挑剔、重边界与失败模式
- Coordinator：稳、会压缩上下文、会控制节奏与风险

这些差异必须服务任务，而不是变成表演。

## Loop 迭代方式

每轮 Holo 迭代必须采用最小可验收切片：

1. 定义本轮目标
2. 列出副作用边界
3. 读取最小必要上下文
4. 修改最少文件
5. 运行本地验证
6. 记录证据路径
7. 总结下一轮最小上下文

默认允许的副作用：
- 本地 repo 文件修改
- 本地验证脚本运行
- 本地 runs 证据写入

必须停下审批的副作用：
- 远程 Git push / MR / merge
- 删除或重置历史
- 外部系统写入
- 生产或预发系统调用
- 权限、通知、部署相关操作

## 验收标准

### 基础验收

- `python3 scripts/build_context.py` 通过
- `python3 scripts/audit_static.py` 通过
- `python3 scripts/verify_deliverable.py` 通过
- 关键定位文档能说明 Holo 与 Loop 的关系
- README 或索引能指向新增定位文档

### 品味层验收

一次迭代不只看“有没有写内容”，还要看：
- 是否减少客服化、补尾、动作水印、电子女友化
- 是否保持硬工作模式零 RP
- 是否让 Agent 的判断更稳定，而不是更迎合
- 是否明确哪些内容属于宪法，哪些只是 traits / reference
- 是否保留留白，不制造过量规则

### 多 Agent 验收

后续接入 Loop 多 Agent 时，需要新增测试或审查项：
- 不同 Agent 的风格是否可区分
- 风格是否服务任务，不抢任务
- 协作中是否能交接上下文而不重复读垃圾信息
- Reviewer 是否能指出品味层退化
- Coordinator 是否能及时压缩上下文并留下 handoff

详细验收清单见 `docs/multi_agent_taste_acceptance.md`。

## Token 与上下文治理

Holo 的迭代不能靠堆长上下文完成。

规则：
- 优先读取索引、标题、摘要，再读取必要正文
- 旧会话大段日志必须压缩为 artifact，不反复带入聊天上下文
- 关键偏好写入 `fusion/XP_PROFILE.md`，后续引用路径，不重复粘贴全文
- 每轮 Loop 结束写 summary，说明下一轮最小上下文
- 如果上下文膨胀、重复、污染判断，先压缩再继续
