# 路由层深度判断标准

> 产出：观澜（标准定义）× 灰钥（执行约束）× 清鉴（治理约束）× 临渊（调度约束）协作
> 日期：2026-07-16
> 状态：待用户审批

## 定位

本标准解决一个结构缺口：路由层在选人格之前，没有"这个问题值不值得多视角对抗"的判断。

当前系统的盲点：路由层只做场景→人格的匹配，不做深度判断。"这个问题需要单视角打穿还是多视角交叉"这个决策，此前只有用户能做。

本标准填补这个缺口。设计决策（四人格对抗共识）：

- **不扩临渊职责**——临渊的认知签名是横向的（任务间调度），深度判断是纵向的（单个问题内部），叠加会撕裂认知签名
- **不加第八人格**——深度判断是路由谓词（布尔值），不是视角，不产出认知内容
- **路由层做 80% 粗筛**，规则给不了结论的 20% 回退用户拍

## 三层分工

| 层 | 职责 | 归属 |
|----|------|------|
| 标准 | "什么问题值得深度对抗"的定义 | 观澜定义，用户审批 |
| 判断 | 把标准编码成评估函数，执行门控 | 路由层 |
| 调度 | 对抗触发后，谁入场、什么顺序、怎么收口 | 临渊 |

三层各管各的。把任何一层的东西塞到另一层，都是 coherence 破坏。

---

## 一、路由层粗筛（80%）

处理明确单视角问题，直接路由到人格，不进深度判断。

### 编码形态

```
route(msg) -> persona:
  signals = extract_signals(msg)
  if signals.explicit_persona:          # 硬信号，直通
      return signals.explicit_persona
  candidate = match_domain(signals)     # 软信号，查映射表
  depth = depth_table[candidate]        # 查表
  if depth == AMBIGUOUS:
      return depth_judge(msg)           # 进深度判断（第二节）
  return candidate
```

### 可硬编码（闭集匹配，命中即走）

- 用户显式点名 → 直通，零判断
- 故障关键词命中（炸了/挂了/告警）→ 镇岳
- 架构关键词命中且无执行动词 → 观澜
- 纯代码动词（改/修/调试/review）且无架构词 → 灰钥

### 必须留模糊（不自动判）

- 思辨转向执行的自然过渡 → 当前人格跟着走，碰到执行动作才切
- 多关键词同现冲突 → 不猜权重，进深度判断
- 深度档位本身 → 进深度判断

### 执行约束（灰钥）

- 深度判断是查表，不是 if-else 堆叠。表是数据，改表不改代码
- 每个判定结果必须能回放：记录命中了哪条 signal、走了哪个档位
- AMBIGUOUS 档必须存在且必须可触达，不能写成"兜底默认走 X"
- 信号抽取独立成函数（`extract_signals`），不散进路由主函数
- 改动边界：加一个查表层 + 一个 AMBIGUOUS 出口 + 一个信号抽取函数，路由主干不重写

## 二、深度判断（20% 模糊地带）

### 核心判据

多视角对抗的触发条件：**单视角判断携带的结构性盲区风险，超过协调成本。**

每个认知签名决定了一组"先注意什么、先忽略什么"。当被忽略的维度恰好是错误的承载面，单视角会给出"自洽但错位"的答案。对抗的职能不是投票，是强制暴露被各自签名遮蔽的约束面。

不满足这个判据的——要么信息不足（回退用户澄清），要么无盲区风险（单视角足够）——都不触发。

### 四个触发维度

每个维度独立判定，**任一命中即触发对抗**（OR 逻辑）。每个维度附判定测试——能跑的 if 条件，不是感觉。

#### 维度一：约束矛盾

**定义**：两条路由规则同时命中，各自指向不同人格，且两个人格的正确行动指令互斥——不是"可以归 A 也可以归 B"的路由歧义，而是"A 的正确动作和 B 的正确动作不能同时执行"。

**判定测试**：
> 能否把两个指令写成两条不能同时成立的命令？
> - 能 → 约束矛盾，触发
> - 不能（只是归属模糊）→ 路由歧义，不触发，回退用户选人格

**典型**：灰钥规则触发"最小改动、复用现有路径"；同时镇岳规则触发"现有路径就是出血点、必须替换"。两条都对，动作互斥。

**反例排除**："这个问题像灰钥也像观澜"——路由层没分干净，归路由歧义，回退用户。

#### 维度二：跨域不可逆

**定义**：问题触及 ≥2 个人格域，且主行动携带不可逆性标记。

**不可逆标记**（穷举，与现有副作用规则对齐）：
- schema 变更（建表/改表/删列）
- 已部署/已构建产物
- 已发送通知
- 已合并契约（接口签名/Dubbo contract/OpenAPI）
- 已删除数据
- 已授予权限
- 已产生外部副作用的外部 API 调用

**判定测试**：
> 1. 行动触及 ≥2 个人格域？
> 2. 行动携带 ≥1 个不可逆标记？
> 两个都 yes → 触发

**关键**：跨域本身不触发。可逆的跨域 → 串行多步执行，不触发。不可逆性是必要条件，不是充分条件；跨域是另一个必要条件。两者同时满足才触发。

**反例排除**：纯本地代码改动，改 5 个文件跨 3 个域，但全可回滚 → 串行，不触发。

#### 维度三：无锚争议

**定义**：争议不存在可检验的正确性判据——不是"我们不知道事实"，而是"知道所有事实后仍然是取舍"。

**判定测试**：
> 如果跑了某条命令 / 写了某个测试 / 查了某个事实，答案会被确定吗？
> - 会 → 不是争议，是无知 → 路由到能消解它的人格（或回退用户）
> - 不会 → 真争议 → 触发

**典型**："替换现有组件 vs 补丁续命"——两者都有真实长期成本，没有指标能一票裁决 → 触发。

**反例排除**："这是 bug 还是 intended behavior" → 查代码/查需求能定 → 不是争议，路由到灰钥查档。

**阈值校准**：争议必须存活过所有可用事实核查才触发。任何一个可用的事实核查能消解它，就先消解，不进对抗。

#### 维度四：结构对立

**定义**：候选方案在结构层分歧——不同的所有权边界、数据流、失败模式或承诺周期。不是实现层分歧。

**判定测试**：
> 反转这个选择，下个迭代需要 >1 天返工吗？
> - 是 → 结构层，触发
> - 否 → 实现层，单视角处理

**补充判据**：
> 候选方案的失败模式是否不同？
> - 失败时炸的地方不一样 → 结构对立，触发
> - 失败时炸同一个地方 → 实现差异，单视角

**典型**：新建服务 vs 进程内模块；同步 vs 异步；自有数据 vs 借用数据。

**反例排除**：变量命名、库版本、函数拆分方式 → 实现层，单视角。

### 组合逻辑

```
触发 = (维度一 OR 维度二 OR 维度三 OR 维度四)
       AND NOT 抑制条件命中
```

**成本门**：维度二命中时，成本门不生效——不可逆性已经把"错了的代价"拉高到协调成本之上。一行 schema 变更也值得对抗。

维度一、三、四命中时，叠加成本门：
> 估计 <30 分钟 AND <1 文件 AND 无外部效果 → 降级回退用户

### 抑制条件

即使维度命中，以下情况不触发对抗：

1. **活跃故障进行中且持续损害** → 镇岳先止血，对抗推迟到 post-mortem。出血时不开会。
2. **用户在上下文中已表达偏好** → 尊重，不对抗。
3. **当前是只读/探索阶段，未提议行动** → 无行动则无不可逆风险，待行动提案出现再判。

抑制条件命中时记录：哪个维度本会触发、哪个抑制条件生效、为何。留痕，不清除触发信号。

### 显式排除（→ 回退用户，不进对抗）

1. **纯路由歧义**：归 A 或 B 都行，无动作互斥 → 用户选人格
2. **信息不足以成帧**：连问题都还没框清楚 → 用户澄清
3. **全员一致**：所有相关人格检视后会一致同意 → 选一个执行
4. **低于成本门且无不可逆**：维度一/三/四命中但问题过小 → 用户比协调快

## 三、调度编排（临渊）

### 入场编排

路由层标记"需多视角对抗"后，传给调度三样东西，缺一不可：

- **靶子命题**：一句话的对抗对象
- **必须覆盖的视角清单**：标准识别的维度对应的人格
- **目标产出形态**：决策 / 风险清单 / 取舍方案

**入场顺序铁律：先发散，后收敛。**

- 发散序在前：观澜、镇岳这类"提约束、提影响"的先说，撑开问题空间
- 收敛序在后：灰钥（执行可行性）、清鉴（模式退化/风险）压尾
- 守门型人格（灰钥、清鉴）不首发——它们是收敛器，先收敛等于没对抗
- 赫罗默认不进技术对抗——除非靶子命题本身是人/关系维度
- 临渊是调度，不参与对抗内容，只编排

### 收口规则

**判断权在调度，不在辩手。** 临渊判断"信息是否充分到可以合成"，不判断"哪方对"。

收口判据（满足任一即可合成）：
- 路由层要求的视角清单已全覆盖
- 连续两轮无新增实质论点，只剩重申和细化
- 分歧已被结构化——从"我觉得不对"收窄成"在约束 X 下，A 牺牲 Y，B 牺牲 Z"
- 出现某人格指出的硬约束，其他视角一致承认绕不开——分歧瞬间消解

**合成产物形态固定**：各方立场 + 不可动约束 + 可取舍点 + 推荐方向
- 推荐方向若在人格能力范围内可定，给推荐
- 若取决于用户价值偏好，标注上交，不替用户拍板

### 中断条件

四个中断条件 + 一个隐性中断：

- **伪对抗**：首个人格发言后，其余视角纷纷表示不涉及/无意见 → 立即中断，按单一视角执行
- **约束消解**：对抗早期某人格抛出硬约束，其他视角立刻一致 → 中断，按约束直接合成
- **降级为单点查证**：跑了两轮发现所有分歧收敛到同一个未决问题，且只需查证 → 中断对抗，转查证
- **越界/空转**：人格跑题或互相抬杠 → 中断当前线程，调度拉回或终止
- **用户可决**（隐性）：发现真正要拍板的是用户价值偏好 → 中断，把取舍点结构化后上交

中断后统一处理：记录中断原因，保留已产生的有效论点不丢弃，转入正确路径。中断不是丢弃，是纠偏。

## 四、治理约束（清鉴）

### 可审计性

每次路由留下可追溯的判定链路：输入特征 → 命中的规则条目 → 人格选择。

审计对象：路由决策的行为记录，不是"标准写得好不好"。
- **审什么**：判定一致性——同类输入在不同上下文是否路由到同一人格。每条规则的判定信号必须外部观察者能复核。
- **硬约束**：不可观测的判定信号 = 不可审计的规则 = 治理盲区，不纳入标准。
- **什么时候审**：定期采样审 + 触发式审（用户质疑路由、人格切换争议、退化信号）。

### 隐形人格约束

路由信号必须用人格无关的中性语言描述。判定"这是不是架构问题"不能用架构师的语言。

**检测工具——替换测试**：把规则里的目标人格名换成另一个。换完后规则仍然逻辑自洽（只是匹配错人）→ 通过。换完后变得荒谬 → 规则嵌入了目标人格认知，不通过，必须改写。

替换测试写进标准附录，作为复审时的固定动作。

### 触发/不触发留痕字段

每次判定留痕：
- 触发维度（一二三四哪个命中，或"无命中"）
- 判定证据（每个命中维度的判定测试结果 + 依据）
- 抑制检查（三个抑制条件各是否命中）
- 最终路径（对抗 / 回退用户 / 单视角串行）
- 替代路径（如果没走对抗，本应走的路径）

不触发也要留痕。审计审的是"该触发没触发"和"不该触发触发了"两类错误。

### 复审约束

标准必须定期复审。触发条件：
1. 人格定义变更——任何 profile/traits 更新，复审涉及该人格的全部规则
2. 退化信号——同类输入路由结果不稳定，或用户频繁质疑路由
3. 隐形人格暴露——替换测试或审计发现嵌入式认知
4. 人格系统扩容——新增人格时全量复审

复审不是重写。逐条核验"判定信号是否仍可观测、是否仍人格无关、是否仍与当前人格定义一致"，只改失效条目。

复审本身要留痕：每次复审结论（哪些有效、哪些改了、为什么）必须记录。

## 附录：替换测试记录

本标准四个触发维度的替换测试结果（2026-07-16 首次审定）：

| 维度 | 判定信号语言 | 替换测试 |
|------|------------|---------|
| 约束矛盾 | 路由规则、行动指令互斥 | 通过——信号是路由层语言，非任何人格认知 |
| 跨域不可逆 | 人格域计数、不可逆标记清单 | 通过——标记来自副作用规则，非人格认知 |
| 无锚争议 | 事实核查可否消解 | 通过——"事实核查"是中性判定 |
| 结构对立 | 返工时间、失败模式差异 | 通过——描述问题特征，非架构师判断 |
